## Confirmed scope

November 8 decisions: Better Auth access sessions with OPAQUE and local vault unlock are the beta default; existing MFA/recovery adapters remain. Switching providers is an explicit disconnect/export/reconnect workflow, without automatic remote migration. The selected official origin is `https://app.ultratasks.app`, reserving `/account` for the dashboard and the root for a future hosted app. Google Drive and collaboration remain later work. Server image `6c903b5974cf1f9697361fea9b2e47e65e76f934` passed native AMD64/ARM64 source and published-image lifecycle checks. These beta decisions do not declare stable server 1.0.0.

- Use **UltraSync** as the working product name for account-based encrypted sync. Do not rename the legacy SuperSync protocol or its persisted provider identifier to UltraSync.
- UltraSync is the first choice in new sync setup, using the official service by default and offering a custom HTTPS endpoint for self-hosting. Sync remains opt-in; offline use needs no account.
- App 0.3.0 ships private personal sync and the account dashboard. Team collaboration remains a later UltraSync feature, available to official and self-hosted installations through the same implementation.
- Keep **OneDrive and WebDAV** as the other new-setup choices, explicitly labeled **Personal sync only — no team collaboration**.
- **Google Drive is dropped for now** (maintainer, November 11). It would be a new provider adapter, and provider sync now receives only security, bug and data-safety fixes ([Decision 11](../../ARCHITECTURE-DECISIONS.md#11-two-remote-sync-engines-provider-sync-receives-fixes-only)).
- Deprecation of other providers means a controlled migration, not disabling configured accounts or deleting credentials/data during an update.

## Sync selection and migration

New setup presents UltraSync first, followed by OneDrive and WebDAV under personal-only alternatives. Explain that personal-only sync includes the user's personal dataset; it does not provide shared projects, invitations, team roles, or member revocation. Sharing a cloud folder must not be presented as collaboration.

UltraSync offers **Official server** and **Custom server**. Only the custom choice needs an endpoint field. The official origin must be configured from verified deployment settings; do not invent a domain or enable a dead sign-in link. Show the selected server before credentials are entered.

Existing Dropbox, Nextcloud, LocalFile, and legacy SuperSync configurations remain readable and usable during the migration window, with a clear deprecation explanation and migration action. Keep persisted provider values, encryption readers, exports, and recovery paths. A Nextcloud user must be able to move to WebDAV using a validated URL/configuration. Local file export/backup remains a separate capability even if LocalFile stops being a new sync choice.

Before changing personal sync mode, flush durable writes, stop the old writer, save a recovery point, and require an explicit upload-to-empty-account or use-existing-account decision. Preserve pending work and require old devices to retire their previous target. Do not silently combine accounts, dual-write a dataset, or erase an old target as part of setup. Concrete legacy removal dates remain a separate release decision after migration evidence exists.

## Authentication implementation decision

The beta uses **Better Auth for hashed access sessions** with `@serenity-kit/opaque` for password authentication. The existing Fastify/Prisma adapter retains rotating refresh tokens, device sessions, password changes, recovery, TOTP, and `@simplewebauthn/server` WebAuthn second-factor enforcement. The encrypted vault uses client-side Argon2id password wrapping and a separate recovery-key wrap. Stock Better Auth plaintext-password endpoints are not exposed. These integration responsibilities remain ours to maintain; adopting Better Auth does not eliminate their security review.

The maintainer selected this bounded Better Auth + OPAQUE integration for the beta on November 8. The server [authentication decision](https://github.com/ultra-tasks/ultra-tasks-server/blob/main/docs/better-auth-prototype.md) records its ownership, migration, and rollback behavior. The native JWT engine remains an explicit operator compatibility option. Authentication fixtures cover both engines; the default deployment selects Better Auth.

The current account password serves two purposes: OPAQUE authentication and local vault unlock. Better Auth's standard [email/password flow](https://better-auth.com/docs/authentication/email-password) sends a password to the server and hashes it there. Sending the existing vault password through that flow would give the server enough material to unwrap the stored vault key. Changing the password hash algorithm does not preserve OPAQUE's boundary.

The implemented integration preserves OPAQUE and the existing local vault unlock, with no second account password. An authenticated framework session does not itself provide encrypted key delivery, passwordless vault unlock, or recovery of encrypted data. Browser login uses the separately reviewed app-bound encrypted handoff and proof-bound one-time redemption.

The decision must demonstrate:

- One coherent account/session lifecycle across direct app login, browser login/return, refresh, revocation, password changes, and recovery; avoid keeping two independent authentication systems indefinitely.
- TOTP and security-key/passkey enforcement on the actual OPAQUE or replacement login path. Better Auth's passkey plugin provides a sign-in method; installing it alongside its TOTP plugin does not by itself establish our intended password-plus-WebAuthn second-factor flow.
- Secure vault unlock and browser-to-app key delivery without exposing the vault password or plaintext keys to the server, URLs, or logs.
- Existing-account migration without account-ID changes, inaccessible vaults, lost MFA enrollment, or silent loss of recovery paths.
- Electron, Android/iOS Capacitor, and browser behavior at both official and custom origins, using the existing platform callback owners and credential stores. Electron support does not establish mobile support.
- Operation inside the self-hosted Docker/PostgreSQL stack, without a mandatory central authentication service.

The server contract records this ownership boundary. Beta adoption intentionally retains the MFA/recovery adapters; replacing those adapters or adding passwordless primary sign-in is outside 0.3.0.

## Sign-in contract

Support direct app login and a complete **Continue in browser** route. Direct password/TOTP login stays available; security-key/passkey prompts may use the selected server's browser origin. For 0.3.0 these are second factors after the account password. Passwordless vault unlock is a separate design, not implied by enabling WebAuthn MFA.

The browser route should use the system browser/authentication session, then return to the initiating app. Follow the external-browser and proof-of-possession principles in [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html); applying those principles does not make the custom OPAQUE/E2EE protocol an OAuth implementation.

Required properties before implementation is called complete:

1. The app creates a bounded, expiring sign-in attempt with a random state, a redeem proof such as PKCE, and an ephemeral recipient key. Bind the attempt to the selected server, installation identity, requesting app, and approved return destination.
2. The account website completes password login, email verification where necessary, and configured MFA. It identifies the requesting app and requires approval before granting it access.
3. The callback contains only an opaque single-use result reference and state. Passwords, reusable access/refresh tokens, recovery keys, and plaintext vault keys never go in a URL, clipboard, page log, or browser history.
4. The app redeems the result using its original proof and authenticates the same server/account identity before installing a session. Reject replayed, expired, canceled, wrong-server, wrong-account, and unrelated callbacks.
5. **Authentication alone does not unlock encrypted data.** An app that never received the password needs a reviewed encrypted key handoff from the unlocked browser to the requesting app, or an explicit local unlock step. The server must not gain plaintext vault keys. Specify this grant's encoding, identity binding, expiry, key deletion, and replay behavior in the server/SDK contract before shipping it.
6. Reuse the existing desktop/native callback owners. Current schemes differ (`ultratasks` on Electron and `app.ultratasks` on mobile); preserve compatibility and add a dedicated account-login route without intercepting provider/plugin OAuth or task-action URLs. Handle both cold launch and an already-running app.
7. Keep device-bound polling/resume as a fallback if the browser cannot open the app. It must require the same proof and approval as automatic return, and must stop on cancellation/expiry. Do not depend on an official-domain callback relay for custom servers.

The exact encrypted handoff is a new security-sensitive protocol surface requiring review and negative tests. Reuse existing primitives where appropriate, but do not claim the current MFA polling flow already implements this full journey.

## Hosted and self-hosted parity

Both deployments use the same API, SDK, dashboard, MFA, E2EE, personal delivery, and future collaboration implementation. Deployment settings control the origin, enrollment, SMTP, resource quotas, and operator documents; they must not replace core functionality with hosted-only authentication or collaboration.

Accounts and vault identities are installation-specific. Selecting a custom server does not move an official account or its data. Make a server/account switch explicit and recoverable. The new installation requires its own account unless an explicit future transfer mechanism is implemented.

WebAuthn credentials are bound to a relying-party identity and validated origins ([WebAuthn Level 3](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/)). A separately hosted domain normally needs its own passkey/security-key enrollment. Each operator needs a stable HTTPS origin and matching WebAuthn configuration. The browser flow must work at that origin without requiring the native app to impersonate it.

Third-party provider OAuth has separate registration/callback requirements. Document those for self-hosted web-client builds; do not promise that an arbitrary web origin can use an official OAuth registration automatically. Google Drive's later implementation should assess [application-data storage and its scope](https://developers.google.com/workspace/drive/api/guides/appdata) and real concurrent-write semantics before being offered as supported sync.

## Sync timing and storage

For active, unlocked, connected UltraSync clients, target ordinary foreground convergence within two seconds under a documented representative workload. Healthy sockets notify promptly; local edits trigger durable capture/upload; HTTP catch-up remains at most a 60-second scheduling interval when notifications are unavailable. This is not a delivery deadline during network failure or mobile suspension. Catch up on resume/reconnect and retain local pending changes through restarts.

Existing full-head downloads have demonstrated significant large-account transfer and latency. Benchmark the actual app with realistic inventories, timers, network delay, and multiple devices, not only SDK microbenchmarks. Reduce unnecessary downloads; design authenticated bounded catch-up if measurements require it, preserving consistent generations, signatures, retry receipts, and atomic transactions. Do not change encryption or persisted semantics merely to lower a timer.

The account dashboard shows actual encrypted-record bytes and quota, plus separately labeled encrypted history. These are server storage measurements, not decrypted task sizes. Keep quota refusal recoverable: retain pending edits and explain that storage needs attention. Existing native bounds remain until a separately validated change is justified.

## Implementation order and release gates

1. Make UltraSync a first-class setup choice with official/custom destinations and personal-only alternatives, preserving active legacy configurations.
2. Resolve the authentication-library decision, then specify and review the full browser-login/key-handoff contract; implement it in the server/SDK and connect all existing platform URL owners. Keep direct login working.
3. Finish the shared account-site MFA/storage journeys and validate them against both deployment types.
4. Prove migration, foreground sync, reconnect/offline recovery, and the large-account envelope using real clients and PostgreSQL.
5. Deploy the official service last, configure the website/app public origin, and complete the beta/security/recovery gates before publishing app 0.3.0.

Release acceptance includes Windows/macOS/Linux Electron, Android, iOS, and the account website in supported browsers. The hosted task application at the origin root is not part of 0.3.0 (see the [hosted web app and account origin plan](2026-11-10-hosted-web-app-and-account-origin.md)). Cover direct login, each MFA method, browser return on cold/warm launch, blocked app return with polling fallback, cancellation/retry, expired/replayed results, server mismatch, account switches, secure credential storage, refresh/revocation, offline edits, and reconnect. Exercise a second independent self-hosted origin, not only the official host with a different label.

Team collaboration is a subsequent milestone; Google Drive is dropped for now. The server's current private profile must remain private until collaboration has its own data-preservation, key rotation, authorization, removal, and cross-client acceptance.

## Beta review evidence — November 8

Release packaging found the initial production bundle at 6.60 MB against the old
6 MB ceiling. SDK 0.1.3 adds a compatible `/client` entry and defers OPAQUE WASM,
reducing the actual initial bundle to 6.18 MB; existing root SDK exports and crypto
formats remain unchanged. The 0.3.0 production/staging ceiling is rebased narrowly
to 6.25 MB for the expanded application, retaining the 5.5 MB warning. The remaining
startup-size warning is a measured beta limitation, not a claim that web performance
has passed Lighthouse acceptance. Native builds package the chunks locally; the PWA
asset group prefetches JavaScript for offline use.

Fresh-context review fixed the saved-provider browser fixtures, the locked/restarted account setup gate, dormant legacy configuration visibility, and successful account-deletion cache cleanup. A real Better Auth two-client regression reproduced silent relinking after explicit disconnect, then passed after deleting only the existing device-local `native-sync-active` metadata row. Local tasks, operations, encrypted queues and the previous remote data remain intact; ordinary lock/restart still resumes the existing connection. No persisted field, wire format, account identifier or encryption format changed.

Focused acceptance passes four setup/legacy browser scenarios, thirty native-sync Angular tests, private offline/concurrent/restart/reconnect browser acceptance, and two browser-login scenarios covering both authentication engines and Windows warm/cold returns. Larger datasets can still require substantial full-head transfers; this is documented as a beta limit rather than a guaranteed two-second delivery deadline. Physical mobile return checks and the independent specialist review remain deferred.
