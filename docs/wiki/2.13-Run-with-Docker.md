# Run with Docker

How to self-host Ultra Tasks's sync server and web app with Docker. There are three separate setups; pick the one that matches what you need:

| You want to…                                                  | Deploy                                                                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Sync the desktop or mobile apps through your own server       | **Sync only:** the separate Ultra Tasks account server (no web app needed)                                             |
| Also use Ultra Tasks in a browser served from your own server | **Web app + sync (optional):** the web app container next to a sync backend; not needed for the desktop or mobile apps |
| Sync through a WebDAV server you already run (e.g. Nextcloud) | **Existing WebDAV:** nothing to deploy; point the apps at your WebDAV server                                           |

To compare the sync providers themselves, see [[2.08-Choose-Sync-Backend]] and [[3.08-Sync-Integration-Comparison]].

## Sync only: Ultra Tasks account server

The account server lives in [ultra-tasks/ultra-tasks-server](https://github.com/ultra-tasks/ultra-tasks-server). Its development image and Compose bundle provide private encrypted account sync and the account dashboard. Stable server 1.0.0 has not been released; review the selected revision's acceptance record before opening enrollment.

Use the [operator installation guide](https://github.com/ultra-tasks/ultra-tasks-server/blob/main/deploy/README.md) for setup, HTTPS/SMTP, persistent identity secrets, enrollment, backups, updates, and fresh-database restore. CI targets native AMD64 and ARM64 Linux. A published image needs Docker/Compose, a domain, and SMTP; it does not need this application repository or npm on the serving machine.

Connect using **Account sync** in the app and the chosen server address. Create and verify your account at that server's /account page. Existing SuperSync providers remain a separate compatibility choice; the new private server does not expose their legacy /api endpoints. Project sharing and the full browser task application are outside server v1.

## Web app + sync

Optional: the desktop and mobile apps do not need it. It is only tested on the same machine; serving it to other devices is up to you.

### Run the web app

No prebuilt Ultra Tasks image is published yet. Build the image from the repository:

```bash
git clone https://github.com/ultra-tasks/ultra-tasks.git
cd ultra-tasks
docker build -t ultra-tasks .
docker run -d -p 8080:80 ultra-tasks
```

Open [http://127.0.0.1:8080](http://127.0.0.1:8080). The build installs the dependencies and compiles the web app inside Docker, so the first build takes a while. The image is built for your host's platform.

**Where your data lives:** the web app keeps all tasks in **each browser's own storage** (IndexedDB) on each device. The container stores nothing. That local copy is neither sync nor a backup: clearing site data, using a private window, or switching browsers or devices starts empty. Use a sync provider to share data between devices, and see [[4.23-Managing-Your-Data]] for backups.

**Same machine vs. other devices:** `http://127.0.0.1:8080` only works on the machine running the container; other devices need an address they can reach, served over HTTPS.

### Add sync

The web app talks to the sync backend from the browser, so the backend must accept that origin:

- **Account sync:** add the web app's exact HTTPS origin to the account server's `CORS_ORIGINS`; see the operator guide above. This is separate from hosting the account dashboard.
- **Existing SuperSync:** configure the legacy server to allow the web app's origin. Its endpoint belongs in the legacy provider settings.
- **WebDAV / Nextcloud:** the WebDAV server must send CORS headers for the web app's origin. Browsers can block WebDAV requests otherwise; the desktop app avoids this.

## Existing WebDAV or Nextcloud

If you already run Nextcloud or another WebDAV server, no extra container is needed (also fine for new setups): pick **Nextcloud** or **WebDAV** in the app, see [[2.09-Configure-Sync-Backend]]. The generic **WebDAV** provider is experimental (the app lists it as "not recommended / no support") because WebDAV servers behave differently.

### Bundled WebDAV example (single-machine try-out)

The repository's `docker-compose.yaml` contains a small example that serves the web app and a WebDAV server from the same host. It is meant for trying things out on one machine, **not** as a validated production or multi-device setup: its WebDAV server cannot reliably detect two devices writing at the same time.

1. Clone the repository; the `app` service is built from it:

   ```bash
   git clone https://github.com/ultra-tasks/ultra-tasks.git
   cd ultra-tasks
   ```

2. Edit `webdav.yaml` before starting: replace the default `admin`/`admin` login, and set usernames, passwords, and per-user directories under `/data` so user data is separate. Do not skip this: Docker publishes ports `8080` and `2345` on all network interfaces, over plain HTTP, so other machines on the network can reach them.

3. Start the stack. Name the two services explicitly — `docker-compose.yaml` also
   defines a `db` and a `supersync` service used only by the E2E test suite, which
   run in test mode and must never be started outside it:

   ```bash
   docker compose up -d --build app webdav
   ```

4. Open [http://127.0.0.1:8080](http://127.0.0.1:8080) for the app. In the app, set up sync with WebDAV base URL: `http://127.0.0.1:2345/`. `127.0.0.1` only reaches the server from the same machine.

### Prefilled WebDAV settings

The web app container can prefill **WebDAV** defaults in the sync settings from environment variables: `WEBDAV_BASE_URL`, `WEBDAV_USERNAME` and `WEBDAV_SYNC_FOLDER_PATH` (setting any of these preselects WebDAV), plus `SYNC_INTERVAL` (minutes), `IS_COMPRESSION_ENABLED` and `IS_ENCRYPTION_ENABLED`. No other provider can be prefilled this way, and no passwords are prefilled. See `docker-compose.yaml` for an example.
